# Decisions log

Defaults chosen where the brief, the application form or the agreement were ambiguous. Each one is
configurable unless marked *(code)*. Client-facing questions are listed in [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md).

| ID | Decision | Why | Where / config key |
|---|---|---|---|
| D-01 | Modular monolith (one FastAPI service, package per module), pure `domain.py` per module for business rules. | Rules are unit-testable without I/O; one deployable is simpler to operate for a CRM of this size. | `backend/app/*/domain.py` |
| D-02 | Membership number = brand prefix + `-` + number. The number is either typed from the paper form or auto-assigned from the company's counter. Search ignores the prefix. | The sample forms show two different prefixes (`MSMC8-` and `MSMMBL-`). | `companies.membership_prefix`, `companies.next_membership_seq` |
| D-03 | Exact membership-number duplicates are blocked (HTTP 409). Matches on mobile, email, PAN or name + DOB need an override reason, which is logged (`DUPLICATE_OVERRIDE`). PAN is compared via an HMAC lookup hash, never decrypted. | As specified; minimises KYC exposure. | `members/duplicates.py` |
| D-04 | Aadhaar: the number is Verhoeff-validated, then only the masked value (`XXXX-XXXX-1234`) is stored. Full storage stays behind a flag that is **off**. | DPDP minimisation; legal basis not yet confirmed. | `kyc.aadhaar_full_storage` |
| D-05 | Last year of use = first year + tenure − 1 (inclusive). Editable with a reason before approval. | The sample (2026 + 10 → 2036) gives 11 years if counted inclusively; see OPEN_QUESTIONS #5. | `members/domain.py:last_year_of_use` |
| D-06 | The down payment can be recorded in Finance when the application is saved (the form's "By:" field), or later from Finance. Approval requires it to be recorded. | 5.3 blocks activation without a down payment, so the demo records it in the conversion step. | `member.require_signed_agreement`, approval check |
| D-07 | A membership year is the calendar year (Jan–Dec), matching "Start Year / First Year of Use". The stay year is the year of check-in. | The forms speak of years, not anniversaries. | *(code)* `entitlement/domain.py` |
| D-08 | Nights are put on hold at `REQUESTED` and deducted at `APPROVED`. Decline releases the hold. | As specified. | `entitlement/service.py` |
| D-09 | Consumption order: oldest saved year → current year → nearest borrowed year. | As specified. | `entitlement.consumption_order` |
| D-10 | Saved nights stay usable until 31-Dec of origin year + `save_years` (default 2). Borrowing reaches `borrow_years` (default 2) ahead, never past the last year of use. A daily job writes `EXPIRED` entries. | As specified. | `entitlement.save_years`, `entitlement.borrow_years` |
| D-11 | Cancellation tiers are inclusive ranges in days from the cancellation date to check-in: ≥31 days → 100%; 15–30 → 50%; 0–14 → 0%. So **exactly 30 or exactly 15 days → 50%**. Cancelling after check-in credits 0. | Brief: "more than 30 days" = 31+; "fewer than 15" = 0–14. | `cancellation_tiers` table |
| D-12 | Partial credits are rounded **down** to the nearest half night (e.g. 50% of 4.5 = 2.25 → 2.0). The credit goes back to the most recent origin year first, so the member keeps the longest-lived nights. | Avoids crediting more than the policy allows; half-nights are supported. | `cancellation_tiers.rounding_mode` |
| D-13 | Tiers apply only to **confirmed** reservations. Cancelling before confirmation releases the hold, or credits back in full if already deducted. Confirmed cancellations need the member's written request (a linked email or document). | The agreement's written-cancellation clause is about confirmed bookings. | `reservations/service.py` |
| D-14 | Each ASF charge (one per member per membership year) is settled by **one** payment of its full base + GST. Partial ASF payments are rejected. GST is fixed at the rate stored on the charge when it was raised. | Keeps GST/receipt arithmetic exact; ASF is a single flat fee. | `finance/service.py` |
| D-15 | Every room booked consumes entitlement (nights × matrix multiplier × rooms). Deductions round **up** to a half night. | The matrix is per unit; multi-room bookings would otherwise be free. | `entitlement.deduction_rounding` |
| D-16 | Alembic baseline `0001` builds the schema from the SQLAlchemy metadata at that revision, then adds triggers, grants and trigram indexes in SQL. Later changes are explicit migrations (autogenerate + review). | A 63-table hand-written baseline adds risk without value. | `backend/alembic/versions/0001_initial.py` |
| D-17 | The season of a stay is the highest-priority season touched by any night (Red > White > Blue). Staff can override it if the calendar has a gap. | Members should not get a peak night at an off-peak deduction. | `seasons.priority`, `season_calendar` |
| D-18 | Booking-window and occupancy problems are **warnings** that need an override reason (or an upgrade charge for occupancy). Gift/Rent requirements are hard rules. | The agreement says requests are fulfilled subject to availability. | `booking.*` settings |
| D-19 | Working days exclude Sundays and the holiday calendar (configurable weekend). | Common Indian business practice. | `booking.weekend_days`, `holiday_calendar` |
| D-20 | Reschedule = `RESCHEDULED` status + a new date version. The existing deduction is adjusted by the difference (`DEDUCTION_ADJUST`) and the reservation must be re-confirmed. A third reschedule needs `reservation.override`. | Never overwrite dates; never deduct twice. | `reservation.max_reschedules` |
| D-21 | Default notice: an `ACTIVE` member with any overdue EMI can be noticed. The deadline is the issue date + 14 days (inclusive). Paying the full overdue amount within the window returns the member to `ACTIVE` automatically. Termination is allowed only after the deadline. | Agreement default clause. | `finance.default_notice_days` |
| D-22 | Payment corrections are `REVERSAL` or `ADJUSTMENT` rows linked to the original. Metadata fixes (reference, remarks, date) are versioned edits with a mandatory reason. Amounts are never edited in place. | As specified. | `payment.correct` |
| D-23 | Receipt numbers: `<receipt_prefix>-<year>-<6-digit seq>`, gap-free per company per calendar year (row-locked counter). | OPEN_QUESTIONS #16. | `companies.receipt_prefix`, `number_sequences` |
| D-24 | The activity log is hash-chained (SHA-256 over the previous hash + canonical JSON). Inserts are serialised with a transaction-scoped advisory lock taken just before commit. UPDATE/DELETE/TRUNCATE are rejected by trigger and revoked from the app role. `record_versions` and `entitlement_ledger` are append-only too. | Tamper evidence. The lock is held only for the final insert. | `audit/service.py`, migration `0001` |
| D-25 | The database transaction is committed by `TransactionalRoute` **before** the response is sent. FastAPI runs yield-dependency teardown after the response, which would let clients see a 2xx before (or despite) a failed commit. | Found by the Playwright e2e (read-after-write 404). | `core/db.py` |
| D-26 | Rate limits are per client IP: login 10/min, everything else 1200/min (offices share one NAT address). Front Door WAF adds a 30/min login rule. | Brute-force protection without blocking a busy office. | `CRM_RATE_LIMIT_*` |
| D-27 | Saved searches are stored per browser (localStorage). A server-side `saved_searches` table exists for sharing later. | Avoids storing personal data in the browser; filters are not personal data. | `useListState.ts` |
| D-28 | Defender for Storage verdicts are picked up by a worker job that polls blob index tags every 2 minutes. The API has no public ingress for an Event Grid webhook. | Keeps the API private. | `refresh_scan_results` |
| D-29 | Next.js `rewrites` are resolved at build time, so the API URL is a Docker build arg. | Same-origin `/api/v1/*` proxy. | `frontend/Dockerfile` |
| D-30 | Demo ASF amounts (₹12,000 Studio / ₹15,000 One-Bedroom), the season calendar and the deduction matrix in `seed_demo.py` are labelled DEMO. The production seed (`app.seed`) contains no prices or rates. | No hard-coded prices. | `app/seed.py`, `app/seed_demo.py` |

## Passwords and account access (docs/PASSWORD_PROMPT.md, Phase 1, 13-11-2026)
| ID | Decision | Why | Where / config key |
|---|---|---|---|
| D-PW-1 | Admins never choose or type a password for anyone. "New user" and "Reset password" both get a **system-generated temporary password** (4 groups of 5 unambiguous characters, about 115 bits), shown once with a copy button. It expires after 24 hours if unused and must be changed at the next sign-in. Only its bcrypt hash is stored. | An admin who chose passwords could know them. Generated ones are strong and can be read out by phone. | `auth/recovery.py`, `password.temp_expiry_hours` |
| D-PW-2 | Forced steps are enforced by the **server**: while `must_change_password` (or `must_enroll_totp`) is set, every route except `/auth/me`, `/auth/logout`, `/auth/change-password` and `/auth/totp/*` returns 403 (`PasswordChangeRequired` / `TotpEnrolmentRequired`). The order is sign in → 2FA code (if on) → change password → (2FA set-up if it was reset). | The UI redirect is only a convenience; nothing else is reachable even through the API. | `core/deps.py:current_user` |
| D-PW-3 | **Resetting another ADMIN needs a second admin.** The reset creates a pending request; a *different* active admin (not the requester, not the target) must approve within 24 hours, otherwise it expires. The request and the approval each need a reason and are logged (`ADMIN_RESET_REQUESTED/APPROVED/REJECTED/CANCELLED/EXPIRED`). **Fallback:** when fewer than two active admins other than the target exist (so no approval is possible), the designated super-admin may reset directly. The super-admin is set by configuration only (`CRM_SUPER_ADMIN_USERNAME`, Terraform `super_admin_username`), never in the UI; the reset is logged as `PASSWORD_RESET_SUPER_ADMIN` and its summary starts with `[SUPER-ADMIN FALLBACK]`. Who it is: OPEN_QUESTIONS 27. | Two-person rule for the most privileged accounts, without locking the business out when only one admin is left. | `auth/recovery.py`, `password.admin_reset_approval_hours` |
| D-PW-4 | **Session revocation by token version.** Every access and refresh token carries `tv`; a password change (with "sign out other devices"), any admin reset and a 2FA reset increment `users.token_version` and revoke all refresh tokens. Old access tokens are refused on their very next request, so there is no 15-minute gap. The check uses the user row the request already loads: **no extra query and no Redis**. Redis caching can be added later if the user lookup itself is ever cached. | Immediate sign-out everywhere at no cost per request. | `core/deps.py`, `auth/service.py:revoke_all_sessions` |
| D-PW-5 | A password reset never touches 2FA, and "Reset 2FA" never touches the password. **2FA can no longer be switched off or replaced by the user**: `/auth/totp/setup` is refused while 2FA is on (before this change, calling it silently disabled 2FA for anyone holding a session). Moving to a new phone is an admin "Reset 2FA" (own permission, reason, logged), after which the user must enrol again before anything else. | A stolen session or a reset must never remove 2FA. | `auth/service.py:begin_totp`, `user.reset_2fa` |
| D-PW-6 | **Password policy** (NIST SP 800-63B): 12–128 characters, no composition rules, no periodic expiry. Rejected: breached passwords (Have I Been Pwned range API with k-anonymity, only the first 5 hex characters of the SHA-1 leave the server, 2-second timeout; bundled top-100k list when the API is unreachable, never blocking the user), anything containing the username, a part of the name (3+ letters) or "club8"/"k8" (case, spaces, dots and dashes ignored), and the current or last 5 passwords (bcrypt hashes). All values are master data. Egress to `api.pwnedpasswords.com:443` is open today (no NSG/firewall on the apps subnet); an FQDN allow-list would need Azure Firewall. | Length and screening beat composition rules; the fallback keeps sign-up working during an outage. | `auth/policy.py`, `auth/breach.py`, `password.*` settings |
| D-PW-7 | Rate limits: sign-in 10/min per IP (existing) **plus 5/min per account**; change password 5/min per account and 30/min per IP (offices share one NAT address). Hitting a limit is logged as `RATE_LIMITED`. The docker-compose stack (local/CI only) raises the sign-in limits for the Playwright suites. | Per-account limits stop guessing one account from many IPs without blocking a busy office. | `CRM_RATE_LIMIT_*`, `core/ratelimit.py` |
| D-PW-8 | Log hygiene: every log record is scrubbed (passwords, tokens, `Bearer`, JWTs, session cookies, sensitive `extra` fields) inside `Logger.makeRecord`, before any handler or the Application Insights exporter sees it. The activity log never contains passwords or hashes (`password_hash` changes are recorded as `***`). A test runs every flow with marker values and searches logs, the activity log and record versions. | Safety net on top of never logging secrets. | `core/logscrub.py`, `test_no_password_or_token_in_logs_activity_log_or_errors` |
| D-PW-9 | **2FA before any password change.** Tokens carry an `mfa` claim: true only when the session passed the TOTP step at sign-in or enrolled 2FA in that session (refresh keeps it). `/auth/change-password` refuses (`MfaRequired`) a user with 2FA on whose session has not passed 2FA, e.g. a session that predates turning 2FA on. With a temporary password the order is therefore sign in → 2FA code → change password; no session exists before the code. | A reset or a stale session must never let a password change bypass 2FA. | `auth/service.py:change_password`, `core/deps.py` |
| D-PW-10 | **Mandatory 2FA per role** (`security.require_2fa_roles`, default `[]`; Admin → Users & roles → "Two-step verification policy", reason required, logged as `SECURITY_POLICY_CHANGED`). Users in a listed role without 2FA must enrol at their next sign-in (`TOTP_ENROLMENT_REQUIRED`), before anything else. ADMIN, MANAGEMENT and FINANCE are marked "Recommended" for Club8 to switch on (OPEN_QUESTIONS 30). | The policy is the business's decision; the switch is ready. | `auth/service.py:_apply_mandatory_2fa` |
| D-PW-11 | **Roles are chosen from the existing roles** (checkbox multi-select), never typed. Every change needs a reason; unknown codes and "no role" are refused; the log entry names the old and new roles and the reason. | Typos used to drop roles silently; role changes are privilege changes. | `PUT /admin/users/{id}/roles` |
| D-PW-12 | **Test isolation.** Backend tests always create and drop their own database (`crm_test_<random>`). The Playwright specs that write data (demo, passwords, tour) refuse to run unless the API reports `e2e_target` (`CRM_E2E_TARGET`, refused in prod), which only `scripts/run_e2e.py` (fresh `crm_e2e` database, API :8001, separate frontend build on :3001) and the CI stack set. The demo database was rebuilt clean on 13-11-2026 after earlier runs had left test accounts in it. | Tests must never write to demo data. | `frontend/e2e/support/stack.ts`, `scripts/run_e2e.py` |
| D-PW-13 | The demo user `demo.admin` has 2FA on with a fixed, FICTITIOUS authenticator key (`DEMOADMINTWOFACTORKEY234`, override `CRM_DEMO_TOTP_SECRET`), documented like the demo password. Demo data only; never seeded in production. | Shows 2FA in demos; tests compute the codes. | `app/seed_demo.py` |
| D-PW-14 | **Forgot password is enumeration-safe.** Every request answers 202 with the same message ("If an account matches, we've sent password reset instructions to its registered email.") and takes at least 0.6 s plus jitter, for existing, unknown, inactive and email-less accounts alike. Lookups match username or registered email; the email always goes to the **registered** address. Unknown identifiers are logged truncated ("ab…"). | Prevents account discovery. | `auth/reset.py` |
| D-PW-15 | **Reset tokens**: 32 random bytes (`secrets.token_urlsafe`), stored as SHA-256 only, compared with `hmac.compare_digest`, valid 30 minutes (`password.reset_token_minutes`), single use; a newer request (or completing a reset) invalidates older unused tokens. The reset page reads the token once and removes it from the address bar (`history.replaceState`); all pages send `Referrer-Policy: no-referrer` and `Cache-Control: no-store`. Links are built from `CRM_APP_BASE_URL` (https required in staging/prod), never from the request's Host header. | Section 2 / 6. | `password_reset_tokens`, migration `0004` |
| D-PW-16 | **Limits**: per account 3/hour and per IP 10/hour (`password.forgot_per_*_per_hour`); over a limit the answer is the same and nothing is sent (`RATE_LIMITED`). CAPTCHA (Turnstile or hCaptcha, `CRM_CAPTCHA_PROVIDER`, keys in Key Vault) after 3 requests per IP per hour (`password.captcha_after_per_ip_per_hour`); the 428 `CaptchaRequired` depends only on the IP, so it reveals nothing about accounts. Off (`none`) until Club8 picks a provider. Abuse caps per IP on the endpoints themselves: `CRM_RATE_LIMIT_FORGOT_IP` / `_RESET_IP`. | Section 2 / 6. | `auth/reset.py` |
| D-PW-17 | **Completing a reset** needs the current TOTP code when 2FA is on (a reset never bypasses or removes 2FA), applies the full password policy, revokes every session, clears any lockout, sets `password_changed_at`, clears a pending temporary password and sends a "Your password was changed" notice. The user is **not** signed in automatically. | Section 2. | `auth/reset.py:complete_reset` |
| D-PW-18 | **Admin reset option A** ("Email a reset link", default when the user has a registered email) and **option B** (temporary password) are both offered; both need a reason, end every session immediately and notify the user by email when they have one. The ADMIN-on-ADMIN approval (D-PW-3) applies to both; the request records the option and the approver's action carries it out. | Section 3. | `auth/recovery.py:_perform` |
| D-PW-19 | **Email**: an `EmailSender` interface with SMTP (Mailpit locally/CI), Azure Communication Services (managed identity; only the endpoint, from Key Vault) and in-memory (tests). Emails are queued with the transaction and sent **after commit** (nothing is sent if it rolls back): by the Dramatiq worker with retries in Azure/docker, or an in-process task with retries locally. A failed or slow send never changes the API response; outcomes are logged (`EMAIL_SENT` / `EMAIL_FAILED`, recipient masked). Bodies are never logged. A reset link travels through Redis only inside the queued job until it is processed. Jinja2 HTML + plain-text templates, branded with the default brand (logo by absolute URL from `CRM_APP_BASE_URL`). No email ever contains a password. | Section 7. | `app/email/` |
| D-PW-20 | **Azure email resources** (Terraform `email.tf`): Email Communication Service + domain (Azure-managed `*.azurecomm.net` until a custom domain is chosen, `email_domain` variable; DNS records in the `email_domain_dns_records` output; DMARC added by hand), Communication Service, domain association, and the app identity as Contributor on the Communication Service only. | No keys to rotate; custom domain pending (OPEN_QUESTIONS 29). | `infra/terraform/modules/crm/email.tf` |
| D-PW-21 | Demo users have FICTITIOUS addresses on the reserved `.test` domain (`demo.sales@example.test` …), so the flows can be shown locally through Mailpit (http://localhost:8025). | Never real staff addresses in seed data. | `app/seed_demo.py` |
